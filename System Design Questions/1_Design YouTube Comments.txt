************* Design YouTube Comments *******************************

Interview Question: Design the frontend architecture for a YouTube-like comment system.

The interviewer isn't primarily asking you to build the UI. They want to know how 
you'd design a comment system that can handle:
            Thousands of comments
            Nested replies
            Likes
            Sorting
            Pagination
            Adding/deleting comments
            Real-time updates
            Loading states
            Performance

1. First clarify the requirements:
----------------------------------
    In an interview, don't immediately start writing components.

    Start by asking: "Should I focus only on the frontend architecture, or should I also discuss backend/API design?"

    Assuming we're designing the frontend, I'd define the requirements.

    ->Functional requirements
      -----------------------
        Users should be able to:
                                View comments
                                Add a comment
                                Edit their comment
                                Delete their comment
                                Like/unlike comments
                                Reply to comments
                                View nested replies
                                Sort comments
                                Load more comments
                                See comment counts
                                See loading/error states
    
    ->Non-functional requirements
      ---------------------------
        The application should:
                                Remain responsive with thousands of comments
                                Avoid unnecessary API calls
                                Avoid unnecessary React re-renders
                                Support mobile and desktop
                                Handle network failures gracefully
                                Be accessible

----------------------
    A simplified YouTube comment section could look like:
                                            Comments
                                        ────────────────────────────

                                        [Write a comment...]

                                        Sort by: Top comments (filter)

                                        ────────────────────────────

                                        👤 John
                                        This video was really helpful!

                                        👍 245    👎    Reply

                                        12 replies
                                        └── Show replies

                                        ────────────────────────────

                                        👤 Sarah
                                        Great explanation!

                                        👍 120    👎    Reply

                                        ────────────────────────────

                                                Load more

3. Component Architecture:
--------------------------
    I'd break the feature into smaller components:
                                                Comments
                                                │
                                                ├── CommentsHeader
                                                │   ├── CommentCount
                                                │   └── SortDropdown
                                                │
                                                ├── CommentInput
                                                │
                                                ├── CommentList
                                                │   │
                                                │   ├── CommentItem
                                                │   │   ├── CommentAuthor
                                                │   │   ├── CommentContent
                                                │   │   ├── CommentActions
                                                │   │   │   ├── LikeButton
                                                │   │   │   ├── DislikeButton
                                                │   │   │   └── ReplyButton
                                                │   │   │
                                                │   │   └── ReplyList
                                                │   │       └── CommentItem
                                                │   │
                                                │   └── LoadingSkeleton
                                                │
                                                └── LoadMore     

    The important principle is: Keep the CommentItem reusable and keep comment-specific logic isolated from the parent.         

4. Data Model:
--------------
    A comment could look like:
        {
            id: "comment_123",
            videoId: "video_456",

            author: {
                id: "user_1",
                name: "John",
                avatar: "..."
            },

            text: "This video was really helpful!",

            likes: 245,
            dislikes: 4,

            userReaction: "like",

            replyCount: 12,

            createdAt: "2026-09-01T10:30:00Z"
        }                              

    For replies:
        {
            id: "reply_123",
            parentId: "comment_123",
            ...
        } 

    I prefer having a parentId rather than putting the entire reply tree inside every comment.

5. API Design:
--------------
    We might have APIs like:

        GET    /videos/:videoId/comments
        GET    /comments/:commentId/replies

        POST   /videos/:videoId/comments

        POST   /comments/:commentId/replies

        PATCH  /comments/:commentId

        DELETE /comments/:commentId

        POST   /comments/:commentId/like

        DELETE /comments/:commentId/like

        For pagination:
            GET /videos/123/comments?sort=top&cursor=abc123&limit=20


        Important:
            I'd prefer cursor-based pagination over offset pagination.

        Why?
            With thousands of comments, offset pagination can become problematic when new comments are inserted.

        Instead of: ?page=5

        we use: ?cursor=abc123

        The backend tells us the cursor for the next batch.

6. Fetching Comments:
---------------------
    If you're using TanStack Query, this is a great use case.

    For example:
                const {
                    data,
                    fetchNextPage,
                    hasNextPage,
                    isFetchingNextPage
                } = useInfiniteQuery({
                    queryKey: ["comments", videoId, sort],
                    queryFn: fetchComments,
                    initialPageParam: null,

                    getNextPageParam: (lastPage) =>
                        lastPage.nextCursor ?? undefined
                });

        The query key is important: ["comments", videoId, sort]

        If the user changes:
                            Video
                                A
                                ↓
                                B

        the cache is separated automatically.

        Similarly:
            Top comments
                ↓
            Newest comments

        creates a different cache entry.

7. Why Infinite Query?
----------------------

    YouTube can have:
            10 comments
            100 comments
            10,000 comments
            1,000,000 comments

    We should never load all comments at once.
            Instead:
                    Initial request
                        ↓
                    20 comments
                        ↓
                    User scrolls
                        ↓
                    Next 20
                        ↓
                    User scrolls
                        ↓
                    Next 20

            This reduces:
                        Network usage
                        Memory consumption
                        Initial rendering cost

8. Nested Replies:
------------------
    One important question is: Should we load all replies together with the parent comment?
                          Ans: No.

        Suppose:
            Comment
            └── 5,000 replies

        Loading all 5,000 replies immediately would be wasteful.

        Instead:
                Comment

                    12 replies
                        ↓
                    Show replies

                When the user clicks: GET /comments/123/replies?cursor=...

                Then load them. We can use another infinite query:

                    useInfiniteQuery({
                        queryKey: ["replies", commentId],
                        ...
                    });

9. State Management:
--------------------

        This is an important interview discussion.
        I wouldn't put everything into Redux.

        I'd divide state into:
            Server state

            Things coming from the backend:
                                        comments
                                        replies
                                        likes
                                        comment counts
                                        user reactions

            Use: TanStack Query

                UI state
                Things such as:
                                currentlyEditingComment
                                replyingToComment
                                openReplySections
                                sortOption

                        These can remain local: useState()

            Global state:
                Only if genuinely needed:
                            authenticatedUser
                            theme
                            global notification state

                Potentially Redux/Zustand/Context depending on the application.

10. Optimistic Like:
--------------------
        Imagine the user clicks: 👍 Like

        We don't want:
                    Click
                    ↓
                    API request
                    ↓
                    wait 500ms
                    ↓
                    UI changes

        Instead:
                Click
                ↓
                UI immediately changes
                ↓
                API request
                ↓
                Success → keep change
                Failure → rollback

        That's an optimistic update.

        With TanStack Query:
                onMutate: async () => {
                  // update cache optimistically
                },

                onError: () => {
                  // rollback
                },

                onSettled: () => {
                  // refetch / synchronize
                }

            This makes the UI feel much faster.

11. Adding Comments:
--------------------

        When the user submits: "Great video!"

        We can optimistically add: Great video!   Sending...

        Then:
            API success
                ↓
            Replace temporary ID
                ↓
            Real comment

            If it fails:
                Failed to post comment
                Retry

12. Avoiding Excessive Re-renders:
----------------------------------

    Imagine: 100 comments

    If one comment receives a like, we don't want:
                                                Comment 1 rerender
                                                Comment 2 rerender
                                                Comment 3 rerender
                                                ...
                                                ...
                                                Comment 100 rerender

    We can use: React.memo(CommentItem)
        and make sure props are stable.

        For example:

        <CommentItem
            comment={comment}
            onLike={handleLike}
        />

    If handleLike is recreated unnecessarily, memoization can become less useful.

    Depending on the architecture, we can use: useCallback()

    for stable callbacks.

13. What if there are 100,000 comments?
---------------------------------------
    This is where the interviewer may push further.

    Pagination alone doesn't solve everything.

    If we've loaded:

        20
        ↓
        20
        ↓
        20
        ↓
        ...
        10,000 comments

    we could still have thousands of DOM nodes.

    For extremely large lists, I'd introduce virtualization.

    ->nstead of rendering:
            10,000 DOM elements

    ->we render approximately:
            20–50 visible items

    ->while scrolling.
        Libraries such as:
                react-window
                TanStack Virtual
                    can help.

    ->The architecture becomes:
                            API Pagination
                                ↓
                            Infinite Query
                                ↓
                            Virtualized List
                                ↓
                            Visible CommentItems

14. Sorting:
------------
    We might support:
                    Top comments
                    Newest first

    Changing the sort should change the query key:
                                                ["comments", videoId, "top"]

    versus: ["comments", videoId, "newest"]

            This allows separate caching.

15. Error Handling:
-------------------
    We should handle failures at different levels.

    ->Initial loading: Loading comments...
    
    ->Network failure: Couldn't load comments.
                        [Retry]

    ->Load more failure:
        Don't destroy already-loaded comments.

        Instead:
            20 comments
            ...
            Couldn't load more comments.
            [Retry]

    ->Comment submission failure:
        Failed to post comment.

        [Retry]

16. Accessibility:
------------------
    This is often forgotten in system-design interviews.

    ->Buttons should have meaningful labels:
            <button aria-label="Like comment">
            👍
            </button>

    ->Reply input should have:
               <label>
                  Reply
                </label>             

    ->Keyboard users should be able to:
            - Navigate buttons
            - Open replies
            - Submit comments
            - Close editing mode

17. Security:
-------------
    Never trust comment content from the client.

    ->The backend should handle:
            - Authentication
            - Authorization
            - Input validation
            - Rate limiting
            - Spam detection
            - XSS protection

    ->For example, don't blindly render:
            <div dangerouslySetInnerHTML={{ __html: comment.text }} />

    If rich text is supported, it needs proper sanitization.

18. Real-time Updates:
----------------------
    ->The interviewer might ask:
            "What if another user adds a comment while I'm watching the video?"

        We could use: WebSocket or Server-Sent Events

        Flow:
            User A posts comment
                    ↓
            Backend
                    ↓
            WebSocket
                    ↓
            User B
                    ↓
            Update React Query cache

        But I wouldn't automatically make the entire comment system real-time unless the product requires it.

        For YouTube-like comments, polling/refetching or refresh-on-focus may be sufficient for many scenarios.

19.

20. Strong Interview Answer: (IMPORTANT)
----------------------------
    If the interviewer says: "Okay, explain your design in 2–3 minutes."

    You could answer:

        "I would divide the comment system into a presentation layer, server-state layer, and UI-state layer. The comment section would have components such as CommentHeader, CommentInput, CommentList, CommentItem, and ReplyList.

        For server state, I'd use TanStack Query with cursor-based infinite pagination because a video can have thousands or even millions of comments. I wouldn't load all comments initially; I'd fetch a small page and fetch additional pages as the user scrolls.

        Replies would also be loaded lazily when the user expands them rather than fetching all nested replies upfront.

        I'd keep temporary UI state such as the comment being edited, the comment being replied to, and the selected sort option locally, while server data would remain in the query cache.

        For likes and adding comments, I'd use optimistic updates so the UI responds immediately and roll back if the API request fails.

        To prevent unnecessary rendering, I'd memoize individual CommentItem components, and if the number of loaded comments becomes very large, I'd introduce list virtualization.

        I'd also handle loading, pagination, and mutation errors independently, and make sure comment content is properly sanitized and that all interactive elements are accessible.

        If real-time comments are a product requirement, I'd add WebSockets or SSE and update the TanStack Query cache when new events arrive."
