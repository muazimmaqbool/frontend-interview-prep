Question 1: How would you design a scalable frontend architecture for a large React application?
             - How would you organize folders and components?
             - How would you separate business logic from UI?
             - How would you ensure maintainability as the application grows?
Answer:
        Start by understanding the app, its teams, and how big it may grow.
        Use a feature-based structure so all related files stay together.

        1. Folder and component organization:
                src/
                    app/                 Routes, providers, and app setup
                    features/
                        auth/
                            components/
                            hooks/
                            api/
                            types/
                        orders/
                            components/
                            hooks/
                            api/
                            utils/
                    shared/
                        ui/              Reusable UI like Button, Input, Modal
                        lib/             Shared utilities and HTTP client
                        styles/          Theme and global styles

                Keep feature files inside each feature. Move reusable pieces to shared/ui.
                Do not keep one giant shared folder. Keep each feature small and clear.
                Expose only a small public API for each feature.

        2. Separate business logic from UI:
                - UI components should only show data and call functions.
                - Custom hooks handle state, fetching, and user actions.
                - API files handle requests and response data.
                - Pure functions handle rules like totals, validation, and filtering.

                Example:
                    OrderPage -> useOrders() -> ordersApi.getOrders()
                    OrderSummary -> calculateOrderTotal(items)

        3. Maintainability:
                Use TypeScript, clean naming, linting, formatting, code reviews, and tests.
                Write clear rules for each module. Keep documentation for important design choices.
                Use CI checks and make feature ownership clear.
                Only use micro-frontends if independent teams and deployment needs really require it.

        Interview answer:
                I group code by feature, keep UI separate from data and business logic, and use clear rules,
                tests, and tooling so the app stays easy to change as it grows.

Question 2: How would you manage state in a large React application?
             - When would you use local state, Context API, or Redux Toolkit?
             - What is the difference between client state and server state?
             - How would you prevent unnecessary re-renders?
Answer:
        First, decide who owns the data and how long it should live.

        1. Choosing where state belongs:
                - Local state: useState/useReducer for input values, modals, and small workflows.
                  Keep the state close to the component that uses it.
                - Context API: share things like theme or locale across a subtree.
                - Redux Toolkit: good for complex shared app state that many features use.
                  It helps with predictable updates and debugging.
                - URL state: filters, sorting, and page numbers that should survive refresh or be shareable.

        2. Client state vs server state:
                Client state is data in the browser, like a form draft or selected tab.
                Server state is data on the backend, like products, permissions, or orders.
                Server state needs fetching, refresh, caching, and revalidation.
                Use TanStack Query or RTK Query for server data instead of keeping the same data in many places.

        3. Reduce unnecessary renders:
                Keep state close to where it is used. Split contexts by responsibility.
                Keep provider values stable when possible. Context updates can make many components re-render.
                Use narrow selectors and avoid storing duplicate data.
                Only add memoization when profiling shows a real performance problem.

        Interview answer:
                I keep UI state local, use Context for shared app values, Redux Toolkit for complex shared state,
                and a query library for server data. Narrow updates help reduce re-renders.

Question 3: How would you design an efficient API data-fetching and caching strategy?
             - How would you avoid duplicate API requests?
             - How would you implement caching using TanStack Query?
             - How would you handle stale data, retries, and cache invalidation?
Answer:
        1. Avoid duplicate requests:
                Use one shared QueryClient and consistent query keys.
                If two parts of the app ask for the same data, they can share the same in-flight request.
                Put all values that affect the response into the key, including user or tenant data.
                Debounce fast-changing search inputs.

        2. TanStack Query example:
                const queryClient = new QueryClient();

                const productsQuery = useQuery({
                    queryKey: ['products', category],
                    queryFn: async ({ signal }) => {
                        const response = await fetch(
                            `/api/products?category=${encodeURIComponent(category)}`,
                            { signal }
                        );
                        if (!response.ok) throw new Error('Unable to load products');
                        return response.json();
                    },
                    staleTime: 60_000,
                    gcTime: 5 * 60_000,
                    retry: 2,
                });

        3. Freshness and failures:
                staleTime tells React Query when data is considered fresh.
                After that, it can refetch in the background when needed.
                gcTime decides when old cached data is removed.
                Retry only for temporary issues like network loss.
                Do not retry permanent errors like bad input or forbidden requests.

        4. Invalidation:
                After a successful product update:
                    queryClient.invalidateQueries({ queryKey: ['products'] });
                This marks matching data as stale. Active data can refetch in the background.
                Use setQueryData when you already know the new result.
                Roll back optimistic updates if a mutation fails.
                Clear user-specific cached data on logout.

        Interview answer:
                I use shared query keys, a single query client, smart cache freshness, and invalidation after mutations
                so the UI stays updated without duplicate requests.

        References:
                https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults
                https://tanstack.com/query/latest/docs/framework/react/guides/que

Question 4: How would you optimize the performance of a large React application?
             - How would you identify performance bottlenecks?
             - When would you use React.memo, useMemo, and useCallback?
             - How would you implement lazy loading, code splitting, and virtualization?
Answer:
        1. Measure first:
                Use React DevTools Profiler to find slow renders.
                Use browser Performance tools to check long tasks and layout work.
                Use Network tools to spot slow requests and large assets.
                Check bundle size and real user metrics like LCP, INP, and CLS.

        2. Memoization:
                - React.memo skips re-rendering a component when its props are the same.
                - useMemo caches a computed value until dependencies change.
                - useCallback caches a function until dependencies change.
                Use memoization only when there is a real reason. Do not add it everywhere.
                If React Compiler is enabled, it may reduce the need for manual memoization.

        3. Load less work:
                Split routes or heavy features using dynamic import and React.lazy:
                    const ReportsPage = lazy(() => import('./ReportsPage'));
                    <Suspense fallback={<Loading />}>
                        <ReportsPage />
                    </Suspense>
                Add an error boundary for failed chunks. Avoid too many tiny chunks.
                Virtualize long lists so only visible rows render.
                Use stable item keys and handle keyboard navigation and variable row heights.

        4. Other improvements:
                Paginate large data, compress images, and set image sizes early.
                Remove unused dependencies and move heavy CPU work to Web Workers if needed.
                Re-test the same interaction after each change.

        Interview answer:
                I first measure the slow part, then reduce heavy renders, large JavaScript bundles, and DOM work with
                memoization, code splitting, virtualization, and asset optimization.

        References:
                https://react.dev/reference/react/memo
                https://react.dev/reference/react/useMemo
                https://react.dev/reference/react/useCallback

Question 5: How would you design authentication and authorization in a frontend application?
             - How would you implement protected routes?
             - How would you handle access tokens, refresh tokens, and session expiration?
             - How would you implement role-based access control (RBAC)?
Answer:
        Authentication means who the user is. Authorization means what they are allowed to do.

        1. Protected routes:
                Check the user session before showing protected pages.
                Show a loading state while checking, redirect to login if not logged in,
                and show a forbidden page when access is denied.
                Keep a return URL so the user can go back after login.
                Also enforce auth rules on the backend for every API call.

        2. Tokens and expiration:
                Prefer backend-managed sessions or a backend-for-frontend setup with Secure, HttpOnly cookies.
                If a browser app must use access tokens, keep them short-lived and avoid storing long-lived tokens in localStorage.
                Refresh tokens should be handled carefully and safely.
                If a request gets a 401, try one refresh and then retry the call once.
                If refresh fails, clear the session and redirect to login.
                Do not refresh forever or on every 403 error.

        3. RBAC:
                Map roles to permissions, such as admin -> users:write and viewer -> users:read.
                Use checks for routes, buttons, and page content, but enforce access on the server too.
                Never trust a role coming from the browser.

        Interview answer:
                I use protected routes, secure session handling, and server-side permission checks.
                This keeps the UI safe and prevents users from doing things they should not do.

        Reference:
                https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html

Question 6: How would you handle errors and failures in a large frontend application?
             - How would you implement global error handling?
             - What are React Error Boundaries?
             - How would you handle API failures, retries, and network disconnections?
Answer:
        1. Global handling:
                Normalize API errors in one shared layer.
                Send unexpected errors to monitoring tools with route, release, and request IDs.
                Do not log private data. Use global listeners for window errors and unhandled rejections.
                Show form-level validation errors near the fields they belong to.

        2. React Error Boundaries:
                Error boundaries catch rendering and lifecycle errors in child components.
                They show a fallback UI instead of crashing the whole page.
                Put boundaries around routes or large widgets so one error does not break the whole app.
                They do not catch all types of errors, like event handler errors or async code outside render.

        3. API and network failures:
                Separate validation, auth, permission, rate-limit, server, and network errors.
                Retry only safe, temporary failures with a limit and backoff.
                Do not retry write requests unless the API supports idempotency keys.
                Keep cached data visible, show connection status, and offer a retry button.
                Listen to online/offline changes, but do not trust them blindly.

        Interview answer:
                I use boundaries for render failures, a shared API error layer for requests, and careful retry logic
                so users still get useful UI even when something breaks.

        Reference:
                https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary

Question 7: What is the difference between CSR, SSR, SSG, and hydration?
             - How does each rendering strategy work?
             - How do they affect SEO and performance?
             - When would you choose Next.js over a traditional React SPA?
Answer:
        1. CSR (Client-Side Rendering):
                The browser downloads JavaScript and then builds the page.
                This works well for interactive apps, but the user may wait longer before seeing content.
                Search engines may not see content as quickly, though some crawlers can run JavaScript.

        2. SSR (Server-Side Rendering):
                The server creates the HTML for each request.
                This helps users see content sooner and helps SEO.
                But the server does more work, so response time can increase.

        3. SSG (Static Site Generation):
                HTML is made ahead of time, usually during build time, and served from a CDN.
                This is great for docs, landing pages, and mostly static content.
                It is fast and cheap to serve, but updates need a rebuild or revalidation.

        4. Hydration:
                Hydration means React connects to already rendered HTML in the browser.
                It makes server-generated pages interactive without reloading the page.
                The server HTML and client output must match closely, or hydration errors can happen.

        5. Choosing Next.js:
                Pick Next.js when you want route-level rendering strategies, server data access, or SEO-friendly pages.
                Use a traditional SPA when the app is mostly browser-based and static hosting is enough.
                SSR and SSG are not automatically faster. You still need to measure server time and client performance.

        Interview answer:
                CSR renders in the browser, SSR renders per request, and SSG prebuilds HTML.
                Hydration connects that HTML to JavaScript. I choose the right strategy based on user need and app type.

        References:
                https://nextjs.org/docs/app/getting-started/server-and-client-components
                https://nextjs.org/docs/14/pages/building-your-application/rendering

Question 8: How would you design a reusable component library or design system?
             - How would you create reusable components?
             - How would you manage themes, styling, and accessibility?
             - How would you maintain consistent UI across multiple applications?
Answer:
        1. Reusable components:
                Start with shared foundations like text, spacing, colors, and interaction patterns.
                Build simple building blocks like Button, Input, Dialog, and Select.
                Give each component clear props, variants, and defaults.
                Keep app-specific logic outside the generic component.

        2. Themes and styling:
                Define design tokens like spacing, colors, and font sizes.
                Use CSS variables for theme support and keep style rules consistent.
                Do not hard-code values in many places.

        3. Accessibility:
                Use native HTML elements, labels, focus states, and keyboard support.
                Keep enough contrast and support screen readers.
                Dialogs should manage focus carefully, and ARIA should only be used when needed.

        4. Consistency across applications:
                Publish a versioned package and document it well.
                Use Storybook, visual checks, and accessibility checks.
                Review changes together and keep migration notes.
                Let teams extend components in supported ways instead of copying code.

        Interview answer:
                I build small, accessible, reusable components with shared design tokens and a clear publishing process.
                That keeps apps consistent and easier to maintain.

Question 9: How would you design a real-time frontend application?
             - When would you use Polling, SSE, or WebSockets?
             - How would you handle reconnection and duplicate messages?
             - How would you manage real-time updates without unnecessary re-renders?
Answer:
        1. Choose a transport:
                - Polling: simple periodic requests for updates that can be delayed a bit.
                - SSE: good for notifications and live feeds, where the server sends updates to the client. (server to client)
                - WebSockets: good for chat, collaboration, and frequent two-way updates.

        2. Connection recovery and correctness:
                Start with a snapshot, then apply updates using a version or cursor.
                This prevents losing events that happen during the initial load.
                Reconnect with a small backoff and jitter.
                Use event IDs to detect duplicates and sequence gaps.
                For client commands, use idempotency keys so retries do not cause double actions.

        3. Efficient React updates:
                Open only one connection from a shared service or provider.
                Update only the affected data in the cache or store.
                Use narrow subscriptions, batch updates, and virtualize long live feeds.
                Clean up listeners and connections when they are no longer needed.

        Interview answer:
                I choose the transport based on timing and communication needs, then design reconnect and deduplication
                so the app stays correct and fast during live updates.

        Reference:
                https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events

Question 10: How would you ensure security in a large frontend application?
              - How would you prevent XSS and CSRF attacks?
              - Where would you store authentication tokens?
              - How would you protect sensitive data and manage environment variables?
Answer:
        1. XSS (Cross-Site Scripting):
                React escapes normal string content by default.
                Do not insert unsafe HTML unless you sanitize it properly.
                Validate untrusted URLs and use a strong Content Security Policy.
                Keep libraries updated. Input validation alone is not enough.

        2. CSRF (Cross-Site Request Forgery):
                If state-changing requests use cookies, the server must validate CSRF tokens or use safe session checks.
                Do not change data with GET requests.
                SameSite cookies help, but they are not the only defense.

        3. Token storage:
                Prefer secure HttpOnly cookies for sessions.
                Do not store long-lived auth tokens in localStorage or sessionStorage.
                If the app must use browser tokens, use short-lived access tokens and a secure refresh flow.
                Even memory storage can still be exposed if malicious scripts run.

        4. Sensitive data and environment variables:
                Use HTTPS, limit returned personal data, and redact logs.
                Enforce auth and authorization on the server for every action.
                Anything in a frontend bundle is public, so do not put secret keys in client code.
                Keep secrets in server-side secret managers, not in the browser.
                Never trust hidden fields, client-only checks, or code obfuscation for security.

        Interview answer:
                I block unsafe content, protect state-changing requests from CSRF, keep credentials out of browser storage,
                and enforce security on the server where it matters most.

        References:
                https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html
                https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html
