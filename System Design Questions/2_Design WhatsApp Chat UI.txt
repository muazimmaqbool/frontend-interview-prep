******************** Design WhatsApp Chat UI *******************************

1. Start by clarifying the requirements:
----------------------------------------
    Functional requirements
            Users should be able to:
                - View a list of chats
                - Open a conversation
                - Send messages
                - Receive messages in real time
                - Send images/files
                - See typing indicators
                - See online/offline status
                - See message status
                - Sending
                - Sent
                - Delivered
                - Read
                - Load older messages
                - Search chats
                - Receive notifications

5. How would I manage state?
----------------------------
    This is where many candidates make a mistake.
    They put everything into Redux.
    I would separate state into categories.

    -> A. Server State:
            Data coming from the backend:
                    Chats
                    Messages
                    Users
                    Online status
                    Message status

            Possible tools:
                    TanStack Query
                    Redux Toolkit Query

            For your stack, I would choose TanStack Query.

    -> B. UI State:
            Things that only control the interface:
                    Selected chat
                    Open attachment menu
                    Typing text
                    Emoji picker
                    Search input
                    Replying to message

            These can use:
                useState

            or a lightweight global store if multiple components need them.

    -> C. Real-Time State:
            Events from WebSocket:
                    NEW_MESSAGE
                    MESSAGE_DELIVERED
                    MESSAGE_READ
                    USER_TYPING
                    USER_ONLINE
                    USER_OFFLINE

            The WebSocket receives events and updates the existing cache/store.


6. Sending a Message:
---------------------
    Let's walk through the complete flow.

    Suppose I type: Hello 👋
                    and click send.

    -> A naive implementation would be:
                Click Send
                    ↓
                Wait for API
                    ↓
                Message appears

            That feels slow.

        Instead, use an optimistic update.

    -> Better flow:
            User clicks SEND
                    │
                    ▼
            Create Temporary Message
                    │
                    ▼
            Add Message to UI immediately
                    │
                    ▼
                API / Socket
                    │
                    ▼
                Server saves
                    │
                    ▼
            Replace Temporary ID
            with Real Message ID

    Visual example:
        You: Hello 👋          ⏳ Sending

        Then: 
            You: Hello 👋          ✓ Sent

7. Message States:
------------------
    A message should have a state.

    For example:
            {
                id: "123",

                clientMessageId: "temporary-uuid",

                conversationId: "456",

                senderId: "user_1",

                content: "Hello!",

                status: "sending",

                createdAt: "..."
            }

    Possible states:
            sending
             ↓
            sent
             ↓
            delivered
             ↓
            read

    Visual flow:
        Message
          │
          ▼
        Sending
          │
          ▼
        Sent
          │
          ▼
        Delivered
          │
          ▼
        Read

    The clientMessageId is important.
    Why?
        Because after reconnecting or retrying, we need to avoid accidentally creating duplicate messages.


8. Preventing Duplicate Messages:
---------------------------------
    Imagine this:
            User sends message
                    │
                    ▼
            Server receives it
                    │
                    ▼
            Network disconnects
                    │
                    ▼
            Client doesn't know whether it succeeded
                    │
                    ▼
            Client retries

    Without a unique client-generated ID:
                Hello
                Hello

            Duplicate message.

            Instead: clientMessageId = UUID

        The backend can treat repeated requests with the same ID as the same message.

         Client
            │
            │ clientMessageId: abc123
            ▼
            Backend
            │
            ├── Already processed?
            │
            ├── Yes → Return existing message
            │
            └── No → Create message

        This is called idempotency.

9. Receiving Messages:
----------------------
    When another user sends a message:
            User A
              │
              ▼
            Backend
              │
              ▼
            WebSocket
              │
              ▼
            User B
              │
              ▼
            Update Message Cache
              │
              ▼
            UI Updates

        On the frontend:
            WebSocket Event
                │
                ▼
            NEW_MESSAGE
                │
                ▼
            Update TanStack Query Cache
                │
                ▼
            MessageList re-renders

        Important point:
                I wouldn't refetch the entire conversation every time a new message arrives.

                Instead:
                        New Message
                            ↓
                        Insert only the new message into the cache

        When the user scrolls upward:
            Scroll ↑

11. The Scroll Problem:
-----------------------
    This is a very good interview discussion.

    Imagine you load older messages.
    Before:
        Scroll Position
        Message 30
        Message 31
        Message 32
    
    Then you load:
        Message 1
        Message 2
        ...
        Message 29
        Message 30
        Message 31
        Message 32

    The UI should not suddenly jump.

    So when older messages are prepended:
        Before Fetch
            ↓
        Save scrollHeight
        Save scrollTop

        Fetch older messages
            ↓
        Prepend messages
            ↓
        Calculate new scrollHeight
            ↓
        Adjust scrollTop

    Conceptually:
        newScrollTop = oldScrollTop + (newScrollHeight - oldScrollHeight)

    This preserves the user's reading position.

    This is a very strong point to mention in an interview.

12. Performance: Virtualization:
--------------------------------
    Imagine 5,000 loaded messages.

    Don't render: 5,000 MessageBubble components
    Instead:
             Viewport
        ┌─────────────────────┐
        │ Message 4900        │
        │ Message 4901        │
        │ Message 4902        │
        │ Message 4903        │
        └─────────────────────┘

        Only visible messages
        + small buffer

        Use: TanStack Virtual

    Architecture:
        API Pagination
            │
            ▼
        Message Cache
            │
            ▼
        Virtualized Message List
            │
            ▼
        Visible Messages Only

13. Typing Indicator:
---------------------
    The user shouldn't send a WebSocket event for every keystroke.
    Bad:
        Key press
           ↓
        WebSocket

        Key press
           ↓
        WebSocket

        Key press
           ↓
        WebSocket

    Instead:
        User starts typing
                │
                ▼
        Send USER_TYPING
                │
                ▼
        Debounce / Throttle
                │
                ▼
        User stops
                │
                ▼
        Send USER_STOPPED_TYPING

    Example: John is typing...
    A debounce of roughly a few hundred milliseconds can reduce unnecessary events.

14. Online/Offline Status:
--------------------------
    Possible events:
        USER_ONLINE
        USER_OFFLINE
        LAST_SEEN_UPDATED

    Flow:
        WebSocket
            │
            ▼
        Presence Event
            │
            ▼
        Update User Cache
            │
            ▼
        Chat Header: "Online"

    For a large application, you don't want every component independently maintaining socket listeners.
    Instead:
                WebSocket Connection
                         │
                         ▼
                 Socket Manager
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Messages       Presence        Typing

       One centralized socket connection is easier to manage.

16. WebSocket Reconnection:
---------------------------
    The connection can drop:
        WebSocket Connected
                │
                ❌
                │
                ▼
        Connection Lost
                │
                ▼
        Retry Connection
                │
                ▼
            Connected

    Don't retry infinitely and aggressively:
            1 sec
            2 sec
            4 sec
            8 sec

        Use exponential backoff.
        After reconnecting:
            Reconnect
                │
                ▼
            Fetch missed messages
                │
                ▼
            Sync local state

    This is important because WebSocket events could have been missed while disconnected.


17. Media Upload:
-----------------
    For images or files:
        User selects image
                │
                ▼
        Upload File
                │
                ▼
        Get File URL
                │
                ▼
        Send Message

    Better architecture for large files:
        Frontend
            │
            ▼
        Request Upload URL
            │
            ▼
        Backend
            │
            ▼
        Signed Upload URL
            │
            ▼
        Frontend uploads directly
            │
            ▼
        Cloud Storage
            │
            ▼
        Send message containing media URL

    This avoids routing large files unnecessarily through the main application server.
