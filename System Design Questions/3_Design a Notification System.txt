Design a Notification System — Frontend System Design:

Assume the interviewer asks:
    Design a notification system for a large web application like LinkedIn, Facebook, or an EMR.

->For a frontend interview, focus on:
     how notifications reach the browser, 
     how they're stored/cached on the client, 
     unread counts, real-time updates, pagination, optimistic updates, and performance.


1. Clarify requirements:
------------------------
    I'd first establish that users should be able:
                     to receive notifications in real time, see an unread badge, open a notification panel, 
                     mark individual notifications as read, mark all as read, navigate to the relevant page, 
                     and load older notifications.

    Example:
                        🔔 3

              ┌────────────────────────┐
              │ Notifications          │
              │                        │
              │ ● John mentioned you   │
              │   2 min ago            │
              │                        │
              │ ● New appointment      │
              │   10 min ago           │
              │                        │
              │   Report completed     │
              │   Yesterday            │
              │                        │
              │      Load more         │
              └────────────────────────┘

    The important frontend requirements are real-time delivery, unread/read state, pagination, caching, deduplication, reconnection, and good performance

            <NotificationItem

4. Notification data model:
---------------------------
    A frontend notification could look like:
        {
            id: "notif_123",

            type: "COMMENT",

            title: "John replied to your comment",

            message: "Nice explanation!",

            isRead: false,

            createdAt: "2026-09-19T10:20:00Z",

            actor: {
                id: "user_22",
                name: "John",
                avatar: "..."
            },

            target: {
                type: "video",
                id: "video_123",
                url: "/videos/video_123"
            }
        }
    Having type is particularly useful.

    For example:
                COMMENT
                MESSAGE
                APPOINTMENT
                PAYMENT
                SYSTEM
                MENTION

    The UI can render each type differently.


5. Initial loading — REST API:
------------------------------
    When the application loads, we don't need to fetch 10,000 notifications.

    Use pagination: GET /notifications?limit=20
        Response:
            {
                notifications: [...],
                unreadCount: 7,
                nextCursor: "abc123"
            }

    Then: GET /notifications?cursor=abc123&limit=20

    I'd prefer cursor-based pagination.
    

6. TanStack Query:
------------------
    Notifications are server state, so TanStack Query is a good fit.

    const notificationsQuery = useInfiniteQuery({
        queryKey: ["notifications"],

        queryFn: ({ pageParam }) => fetchNotifications(pageParam),

        initialPageParam: null,

        getNextPageParam: (lastPage) =>
            lastPage.nextCursor ?? undefined
    });

    Now we get:
        Server
          ↓
        TanStack Query
          ↓
        Query Cache
          ↓
        NotificationPanel

    We don't need to copy all of that data into Redux.


7. Real-time notifications:
---------------------------
    This is the most important part of this system-design question.

    Imagine another user mentions me.
        User A
        │
        │ mentions User B
        ▼
     Backend
        │
        │ notification event
        ▼
      WebSocket
        │
        ▼
        User B's Browser

    Frontend listens for something like:
        socket.on("notification", (notification) => {
            ...
        });

    When a notification arrives, we update the query cache.
        Conceptually:
            queryClient.setQueryData(
                ["notifications"],
                oldData => {
                    // add notification to the beginning
                }
            );

    The UI immediately becomes: 🔔 3 to 🔔 4 without refreshing the page.


8. Why both REST and WebSocket?
-------------------------------
    This is a very common follow-up.
    I'd explain:
        WebSockets are used to receive new events, while REST is used to retrieve the persistent notification history.

    ->Suppose I haven't opened the application for three days.
    ->WebSocket can't magically give me all historical notifications unless the protocol is designed to replay them.

    So when I return after 3 days:
                    Application opens
                            │
                            ▼
                    GET /notifications
                            │
                            ▼
                    Existing history

    After connection:
                WebSocket
                   │
                   ▼
           New notifications

    So,
        REST      → History / pagination / mutations
        WebSocket → Real-time events

    This distinction is excellent to mention in an interview.


9. Unread count:
----------------
    Don't calculate the unread count by downloading every notification.

    -> Bad approach:
            notifications.filter(n => !n.isRead).length

        Imagine the user has: 32,000 notifications

        but the frontend loaded only 20.

    -> Instead the backend should provide:
            {
                unreadCount: 37
            }

    Frontend can keep/cache that value.
                 🔔
                ┌───┐
                │37 │
                └───┘
    When a real-time notification arrives: 37 → 38
    When one is marked read: 38 → 37


10. Mark notification as read:
------------------------------
    When the user clicks: ● John mentioned you
        we could call: PATCH /notifications/notif_123/read

        But I wouldn't wait for the API before changing the UI.
        Use an optimistic update:
            User clicks
                │
                ▼
            Update UI immediately

            ● Notification
                ↓
            Notification
                │
                ▼
            Send API request

        If it API succeeds: keep state

        If it fails: rollback

        Same concept for: Mark all as read


11. What happens when WebSocket disconnects?
--------------------------------------------
    This is where you can demonstrate stronger frontend knowledge.

    Connections can fail because of:
                    Wi-Fi lost
                    Laptop sleeps
                    Server restart
                    Network switches
                    Browser backgrounding

    Don't assume WebSocket stays connected forever.
                    Connected
                        │
                        X
                    Disconnected
                        │
                        ▼
                    Reconnect
                        │
                        ▼
                    Re-sync notifications

    Use exponential backoff for reconnection:   
                    1 sec
                    2 sec
                    4 sec
                    8 sec
                    ...

    After reconnection, refetch notifications or request events since the last known cursor/timestamp.
    This prevents missed notifications.


12. Duplicate notifications:
----------------------------
    Consider this:
        WebSocket receives Notification #123
                        +
        REST refetch returns Notification #123

    Without handling this, we might show:
        John mentioned you
        John mentioned you

    Each notification should therefore have a unique:
        notification.id

    and we should deduplicate by ID when merging server results and real-time events.


13. Browser notification vs in-app notification:
------------------------------------------------
    Another useful distinction:

    -> In-app:
          🔔 4
        Displayed inside the application.

    -> Browser push:
        ┌─────────────────────────┐
        │ You have a new message  │
        │ John: Hey!              │
        └─────────────────────────┘

        Browser push is a different layer, commonly involving:
                    Service Worker
                        +
                    Push API

        So I'd mention it as an optional extension rather than mixing it into the core in-app design.

    
14. Performance:
----------------
    Suppose a user has: 100,000 notifications

    We don't render them all.
    Use:
        Cursor pagination
            +
        Infinite loading

    If the UI accumulates a very large list, introduce virtualization: TanStack Virtual
    
    or another virtual-list implementation.
        The browser might then render only: 20–40 visible notifications
        instead of thousands of DOM elements.
