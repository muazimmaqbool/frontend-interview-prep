Part 1. Rendering & Delivery Models:
    These concepts help you decide where and when your application's HTML should be generated.

----------------------------------------------------------------------------------------------------------------------
1. What is Static Site Generation (SSG), and how does it work?
Answer:
    SSG generates HTML pages at build time instead of generating them for every incoming request.

    The process:
        1. During the build, the framework fetches the required data.
        2. It generates HTML files for each route.
        3. These files are deployed to a CDN or hosting provider.
        4. When a user visits the page, the pre-generated HTML is delivered immediately.

    Advantages:
        - Very fast initial page delivery.
        - Excellent SEO because HTML is available immediately.
        - Easy to scale using CDN caching.
        - Less computation required per request.

    Disadvantages:
        - Content can become outdated.
        - Updating content may require rebuilding the site.

    Real-world example: Documentation websites, blogs and marketing websites.

    Que: Interview follow-up: What happens if the content changes after the build?
    Ans: You need to rebuild and redeploy the page, unless you use a mechanism such as ISR.


-----------------------------------------------------------------------------------------------------------------
2. What is Incremental Static Regeneration (ISR), and how is it different from SSG?
Answer:
    ISR allows statically generated pages to be regenerated after deployment without rebuilding the entire application.

    For example, consider an e-commerce product page.
        - Product description rarely changes.
        - Product price may change periodically.
        - Stock availability may change frequently.
    
    With ISR, you can configure a revalidation interval.

    When the page becomes stale, a visitor can trigger background regeneration. 
    The previously generated version can be served while the new version is generated.

    SSG	                                       ISR
    ---------------------------------------------------------------------------------------------
    Generated at build time	               |   Generated at build time and regenerated later
    Requires rebuild/redeploy to update	   |   Can update individual pages
    Suitable for mostly static content	   |   Suitable for periodically changing content

    ->Important: ISR does not automatically make every piece of data real-time. Frequently changing data may still need API requests.


----------------------------------------------------------------------------------------------------------------------
3. What is Server-Side Rendering (SSR)?
Answer:
    SSR generates HTML on the server for each incoming request.

    The process:
        1. User requests a page.
        2. Server receives the request.
        3. Server fetches the required data.
        4. Server generates HTML.
        5. Browser receives the rendered HTML.
        6. JavaScript hydrates the page to make it interactive.

    Advantages:
        - Fresh content on each request.
        - Better initial HTML availability for SEO.
        - Supports personalized content.
        - Useful for dynamic pages.

    Disadvantages:
        - More server computation.
        - Can increase response time under heavy traffic.
        - Requires careful caching and server resource management.

    Real-world examples: Personalized dashboards, user profiles and social media feeds.


----------------------------------------------------------------------------------------------------------------------
4. What is Client-Side Rendering (CSR)?
Answer:
    CSR means the browser handles most of the rendering work.

    The server initially sends a basic HTML document and JavaScript bundles. The browser executes JavaScript, fetches API data and builds the UI.

    For example, in a React application created using Vite:
        1. Browser requests the application.
        2. Server returns HTML and JavaScript assets.
        3. React initializes.
        4. Components render.
        5. API requests fetch application data.
        6. React updates the UI.

    Advantages:
        - Excellent interactivity.
        - Smooth navigation after initial loading.
        - Less server-side rendering computation.
        - Suitable for complex applications.

    Disadvantages:
        - Initial loading can be slower.
        - Large JavaScript bundles can affect performance.
        - SEO can require additional rendering strategies.

    Real-world examples: Figma-like editors, internal dashboards and complex SaaS applications.


----------------------------------------------------------------------------------------------------------------------
5. What is Hybrid Rendering? Why would you use it?
Answer:
    Hybrid rendering combines multiple rendering approaches within the same application.

    You don't have to choose only SSR, CSR or SSG for your entire application.

    For example, consider an e-commerce application:
        Page	            Rendering strategy	     Reason
        -----------------------------------------------------------------------
        Homepage	      | SSG	                  |  Mostly static content
        Product listing	  | SSG/ISR	              |  Cached catalog
        Product details	  | ISR	                  |  Periodically changing content
        User profile	  | SSR	                  |  Personalized content
        Shopping cart	  | CSR	                  |  Highly interactive

    Why use it?
        It allows you to optimize each route according to its requirements rather than applying one rendering strategy everywhere.


----------------------------------------------------------------------------------------------------------------------
6. What is a CDN, and how does Edge Delivery improve performance?
Answer:
    A Content Delivery Network (CDN) is a geographically distributed network of servers that stores cached copies of content.

    Without a CDN:
        A user in India might need to download assets from a server located in the US.

    With a CDN:
        The user can receive cached assets from a nearby CDN location.

    Edge delivery takes this further by allowing computation and, in some architectures, rendering to happen closer to users.

    Benefits:
        - Reduced network latency.
        - Faster asset delivery.
        - Reduced load on the origin server.
        - Better global scalability.

    Interview follow-up: Does a CDN cache everything?

    No. Static assets are commonly cached, while personalized or sensitive responses require carefully configured caching policies. 
        Incorrectly caching private responses can expose user data.

Part 2. Performance & Optimization:
    These concepts are particularly important when designing applications with large bundles, complex dashboards and thousands of records.

----------------------------------------------------------------------------------------------------------------------
7. What are TTFB, FCP, LCP and CLS?
Answer:
    These are important frontend performance metrics.
    Metric	       Meaning	                    What it measures
    ------------------------------------------------------------------------------------
    TTF       Time to First Byte	         How quickly the server starts responding
    FCP	      First Contentful Paint	     When the first visible content appears
    LCP	      Largest Contentful Paint	     When the largest visible content element appears
    CLS	      Cumulative Layout Shift	     Unexpected movement of page elements

    Example:
        Imagine opening a dashboard:
            - TTFB: Browser receives the first response bytes.
            - FCP: Header or loading indicator appears.
            - LCP: Main dashboard chart becomes visible.
            - CLS: The chart suddenly shifts downward because its container had no reserved height.
            
        How do you improve them?
            - TTFB: Improve server response time, CDN usage and caching.
            - FCP: Reduce render-blocking resources.
            - LCP: Optimize hero images, fonts and critical resources.
            - CLS: Reserve image dimensions and avoid injecting unexpected content.

    
----------------------------------------------------------------------------------------------------------------------
8. What is Lazy Loading? How would you implement it in React?
Answer:
    Lazy loading means loading resources only when they are needed instead of loading everything during the initial page load.

    For example, if an application has 20 routes, loading JavaScript for all 20 routes immediately can increase the initial bundle size.

    React provides React.lazy() and Suspense.

    Example:
        import { lazy, Suspense } from "react";
        const Reports = lazy(() => import("./Reports"));

        function App() {
            return (
                <Suspense fallback={<p>Loading reports...</p>}>
                    <Reports />
                </Suspense>
            );
        }

    Now the Reports component can be downloaded/Rendered when it is needed.

    Other examples:
        - Lazy-loading images.
        - Loading modals only when opened.
        - Loading heavy charts on demand.
        - Loading components when they enter the viewport.

    Que: Interview follow-up: What is the difference between lazy loading and code splitting?
    Ans: Code splitting divides JavaScript into smaller bundles. Lazy loading determines when those bundles should be loaded.


----------------------------------------------------------------------------------------------------------------------
9. What are Service Workers, and how do they help with caching?
Answer:
    A service worker is a JavaScript script that runs separately from the main browser page.

    It can intercept network requests and implement caching strategies.

    For example:
        A user opens a news application for the first time.
            1. The service worker caches important application assets.
            2. The user closes the browser.
            3. The user opens the application again without internet.
            4. The service worker serves cached assets.
            5. The application can display previously cached content.

    Common caching strategies:
        - Cache First: Check cache before requesting the network.
        - Network First: Try the network first, then use cached data if necessary.
        - Stale While Revalidate: Return cached data immediately while updating it in the background.

    Important: A service worker does not automatically make every API request work offline. 
               You must implement appropriate caching and data synchronization strategies.

Part 3. Data & State Management:
    This is one of the most important sections for React developers because choosing the right data ownership model directly affects application maintainability.

----------------------------------------------------------------------------------------------------------------------
10. What is the difference between Local State, Global State and Server State?
Answer:
    These three categories represent different types of application data.

    1. Local State: State that belongs to a particular component.

        Example: const [isOpen, setIsOpen] = useState(false);
        Use it for:
            - Modal visibility.
            - Input fields.
            - Dropdown states.
            - Component-specific interactions.

    2. Global State: State that multiple components or pages need to access.

        Examples:
            - Authenticated user.
            - Selected clinic/Gym/Etc.
            - Theme preferences.
            - Application-wide configuration.

        Tools include Redux, Zustand and React Context.

    3. Server State: Data that originates from an external server or API.

        Examples:
            - Doctor listings.
            - Patient records.
            - User profiles.
            - Appointment information.

        Tools such as TanStack Query help manage server state.

        They provide:
            - Caching.
            - Background refetching.
            - Request deduplication.
            - Loading and error states.
            - Cache invalidation.

    Senior-level question: Why shouldn't you store all API responses in Redux?

    Because server state has a different lifecycle from client-owned state. 
            It requires caching, synchronization, refetching and invalidation. 
            A dedicated server-state solution can manage these concerns more effectively.


---------------------------------------------------------------------------------------------------------
11. How does API caching with expiration work?
Answer:
    API caching stores previously fetched responses so that the application doesn't need to request the same information repeatedly.

    For example:
        A dashboard fetches clinic information.
            - First request: API is called.
            - Response: Stored in cache.
            - Second request: Cached response is returned.
            - After expiration: Data is fetched again.

    Common browser storage options:
        Storage	         Characteristics	              Suitable for
        ---------------------------------------------------------------------
        In-memory	 |  Fast, temporary	               | Current session data
        localStorage |	Persistent key-value storage   | Small non-sensitive preferences
        IndexedDB	 |  Persistent structured storage  | Larger datasets and offline data

    Important: Browser caching must account for stale data, invalidation, storage limits and security. 
               Never treat client-side cached data as the source of truth for authorization.


---------------------------------------------------------------------------------------------------------
12. What is the difference between REST and GraphQL?
Answer:
    REST and GraphQL are two approaches to designing APIs.

    ->REST: Uses multiple resource-based endpoints.
        For example:
            GET /api/users/10
            GET /api/users/10/posts
            GET /api/posts/20/comments

        Sometimes the frontend receives more data than it needs or requires several requests to construct a screen.
    
    ->GraphQL: Allows the client to request specific fields through a query.
        Example:
            query {
                user(id: 10) {
                    name
                    posts {
                    title
                    comments {
                        message
                    }
                  }
                }
            }
        The server returns the requested fields.

    ->Difference between REST and GraphQL:
        REST	                                    GraphQL
        ---------------------------------------------------------------------------
        Multiple resource endpoints	      |    Commonly a single GraphQL endpoint
        Response structure defined by API |    Client selects requested fields
        Straightforward HTTP caching	  |    Requires more deliberate caching
        Simpler for many standard APIs	  |    Useful for complex data requirements

    ->Que: Senior-level question: Is GraphQL always faster than REST?
      Ans:No.
        GraphQL can reduce over-fetching and multiple client requests, but it can introduce expensive resolver execution, N+1 query problems and more complex caching.
        The correct choice depends on the application's requirements.

13. What is the difference between Offset Pagination and Cursor Pagination?
Answer:
    Both techniques divide large datasets into smaller chunks.

    -> Offset Pagination:
        You request records based on the number of records to skip.
        GET /api/doctors?limit=20&offset=40

        This retrieves 20 records after skipping the first 40.

        Advantages:
            - Easy to implement.
            - Supports numbered pages.
            - Useful for relatively stable datasets.
        Disadvantages:
            - Large offsets can become expensive.
            - New records can shift positions.
            - Can cause missing or duplicated records when data changes.

    ->Cursor Pagination:
        Uses a cursor representing the position of the last returned record.
        GET /api/doctors?limit=20&cursor=doctor_125

        The next request retrieves records after that cursor.

        Advantages:
            - More reliable for changing datasets.
            - Suitable for infinite scrolling.
            - Avoids many offset-related consistency problems.
        Disadvantages:
            - More complex implementation.
            - Direct navigation to arbitrary page numbers is less natural.
    
    ->Real-world examples:
        - Offset: Admin tables with numbered pages.
        - Cursor: Social media feeds, notifications and chat messages.

    
----------------------------------------------------------------------------------------------------------
14. What is the difference between WebSockets, Server-Sent Events (SSE) and Polling?
Answer:
    All three techniques allow applications to receive updated information from servers.

    1. Polling:
        The browser repeatedly requests information from the server.
        setInterval(() => {
            fetch("/api/notifications");
        }, 5000);

        Advantages:
            - Simple to implement.
            - Works with standard HTTP.
        Disadvantages:
            - Repeated unnecessary requests.
            - Updates may be delayed.
            - Can increase server load.

    2. Server-Sent Events (SSE):
        The server pushes updates to the browser through a persistent HTTP connection.
        Communication is one-way: server to client.

        Example: const source = new EventSource("/api/events");

        source.onmessage = (event) => {
         console.log(event.data);
        };

        Useful for:
            - Live notifications.
            - Stock prices.
            - Server logs.
            - Live dashboards.

    3. WebSockets:
        WebSockets provide persistent, bidirectional communication.
        Both client and server can send messages whenever needed.
        
        const socket = new WebSocket("wss://example.com");

        socket.onmessage = (event) => {
            console.log(event.data);
        };

        socket.onopen = () => {
            socket.send("Hello server");
        };

        Useful for:
            - Chat applications.
            - Multiplayer games.
            - Collaborative editors.
            - Real-time communication.

    ->    Feature	             Polling	              SSE	               WebSockets
        --------------------------------------------------------------------------------------
        Communication	      | Client requests	    |  Server pushes	 |   Both directions
        Persistent connection |  No	                |    Yes	         |   Yes
        Real-time efficiency  |	 Lower	            |    Good	         |   Good
        Complexity	          |  Low	            |    Medium	         |   Higher

    Que: Interview follow-up: Would you use WebSockets for a notification system?
    Ans: Not necessarily. 
         If notifications only need to flow from server to client, SSE may be simpler. 
         If the application needs bidirectional real-time communication, WebSockets are a stronger choice.

15. What are Micro Frontends? Why would an organization use them?
Answer:
    Micro Frontends divide a large frontend application into smaller, independently developed and deployed applications.

    Imagine an enterprise healthcare application with these modules:
        - Patient Management.
        - Doctor Dashboard.
        - Appointment Management.
        - Billing.
        - Reports.

    Different teams can own different modules:
        -> They can develop, test and deploy their modules independently while the modules work together as one application.
        -> Module Federation is one technique that allows independently built applications to expose and consume modules at runtime.

    Advantages:
        - Independent deployments.
        - Parallel development.
        - Team autonomy.
        - Clearer ownership.

    Disadvantages:
        - More architectural complexity.
        - Dependency management challenges.
        - Potential duplication of shared libraries.
        - Cross-application communication becomes harder.

    Que: Senior-level question: Should every React application use micro frontends?
    Ans: No. A modular monolith is often simpler for small and medium-sized teams.

    Note: Micro frontends become valuable when organizational boundaries, independent deployment requirements and team ownership justify their additional complexity.

16. What is Component-Based Architecture and a Design System?
Answer:
    Component-based architecture divides an application into reusable UI components.

    For example:
        Application
            │
            ├── Layout
            │   ├── Header
            │   ├── Sidebar
            │   └── Footer
            │
            ├── Common Components
            │   ├── Button
            │   ├── Input
            │   ├── Modal
            │   └── Table
            │
            └── Features
                ├── Patients
                ├── Appointments
                └── Reports

    A design system goes beyond reusable components.
    It defines:
        - Design tokens.
        - Colors.
        - Typography.
        - Spacing.
        - Component variants.
        - Interaction patterns.
        - Accessibility guidelines.

    Examples include Shopify Polaris and IBM Carbon.

    ->Why is this important?
        Without a shared design system, different teams may implement buttons, forms and modals differently.
        A design system creates consistency and reduces duplicated development work.

    Que: Senior-level follow-up: What's the difference between a component library and a design system?
    Ans: A component library provides reusable UI components. 
         A design system includes the broader design principles, tokens, guidelines and patterns that govern how those components should be used.

17. What is CI/CD in frontend development?

    CI/CD automates the process of integrating, testing and deploying frontend code.
    A typical pipeline looks like this:
        Developer pushes code
                |
                v
        Git Repository
                |
                v
        CI Pipeline
                |

        - GitLab CI/CD.
        - Jenkins.

    Que: Senior-level question: How would you prevent a broken frontend deployment from affecting all users?

            - Preview deployments.
            - Staging environments.
            - Feature flags.
            - Canary releases. 
            - Rollback mechanisms.

    Note: What is a canary releases:
          Ans: A canary release (or canary deployment) is a software development practice where a new version of an application is rolled out 
              to a small subset of users or servers before releasing it to the entire user base

18. What is Accessibility (a11y), and why is it important in frontend architecture?
Answer:
    Accessibility means designing applications that can be used by people with different abilities, including people who rely on assistive technologies.

    Important considerations:
        1. Semantic HTML:
            Prefer:
                <button onClick={handleSubmit}>
                    Submit
                </button>

            Instead of:
                <div onClick={handleSubmit}>
                    Submit
                </div>


    2. Keyboard Navigation: Users should be able to navigate and interact using a keyboard.

    3. Screen Reader Support: Use meaningful labels, accessible names and appropriate ARIA attributes where necessary.

    4. Color Contrast: Ensure text remains readable against its background.

    5. Responsive Design: The application should work across different screen sizes.

    Note: Accessibility should be considered during component design, not added as an afterthought.


-----------------------------------------------------------------------------------------------------------
19. What is a Progressive Web App (PWA), and how does Offline-First architecture work?
Answer:
    A Progressive Web App is a web application that can provide app-like capabilities, including installation and offline functionality.

    The major building blocks are:

        1. Service Worker: Runs in the background and intercepts network requests to implement caching.

        2. Web App Manifest:
            Defines application metadata such as:
                - App name.
                - Icons.
                - Theme color.
                - Display mode.
                - Start URL.

        3. HTTPS: secure communication and is required for service workers in normal production environments.

    -> Offline-first architecture means designing the application to remain useful when the network is unavailable.
        For example, a field-service application could:
            1. Cache essential application files.
            2. Store selected records in IndexedDB.
            3. Allow users to create records offline.
            4. Queue pending changes.
            5. Synchronize changes when connectivity returns.

    Que: Senior-level follow-up: What happens when two users update the same record while offline?
    Ans: You need a conflict-resolution strategy, such as version checks, timestamps, server-side reconciliation or domain-specific merge rules. 
         Simply synchronizing queued requests is not enough.

20. Explain XSS, CSRF, CSP and frontend authentication security.
Answer:
    These are important web security concepts.

    1. XSS – Cross-Site Scripting: 
        An attacker injects malicious JavaScript into a web page.

        Example:
            If an application renders untrusted user input as HTML without sanitization, an attacker might inject a script that executes in another user's browser.

        Prevention:
            - Avoid unsafe HTML injection.
            - Escape untrusted content.
            - Sanitize HTML when rendering user-generated markup.
            - Implement Content Security Policy.

    2. CSRF – Cross-Site Request Forgery:
        An attacker tricks an authenticated user's browser into making an unwanted request to another website.

        Prevention:
            - CSRF tokens.
            - SameSite cookie configuration.
            - Origin/Referer validation where appropriate.

    3. CSP – Content Security Policy:
        CSP is a browser security mechanism that controls which sources are allowed to load scripts, styles and other resources.
        It helps reduce the impact of certain XSS attacks.

    4. Authentication Security:
        Frontend applications must handle authentication credentials carefully.

        Consider:
            - Secure cookie configuration.
            - Token expiration.
            - Refresh token rotation.
            - HTTPS.

        - Avoiding sensitive credentials in localStorage when safer alternatives are available.
    
    Que: Senior-level question: Is storing a JWT in localStorage completely safe?
    Ans: No. JavaScript running in the same origin can access localStorage. If an attacker successfully executes XSS, they may steal the token.
         An HttpOnly cookie prevents JavaScript from directly reading the cookie, although cookie-based authentication needs appropriate CSRF protection.

21. What is Frontend Observability, and how do you monitor production errors?
Answer:
    Frontend observability is the ability to understand what is happening inside an application using collected runtime, performance and user-interaction information.

    It helps answer:
        - Why did the application crash?
        - Which component caused an error?
        - Which browser is affected?
        - Which API is failing?
        - Why is a page loading slowly?
        - What actions did the user perform before encountering an issue?

    Important areas:
        1. Error Monitoring:
            Track JavaScript exceptions, failed API requests and React rendering errors.

        2. Performance Monitoring:
            Track page loading, slow components and Core Web Vitals.

        3. User Session Insights:
            Understand the sequence of interactions that led to an issue, subject to privacy controls.

    Popular tools:
        - Sentry.
        - LogRocket.
        - Google Lighthouse.

    Example: After deploying a new version of your React application, users report that the patient registration form crashes.

    With frontend monitoring, you can investigate:
        - Error stack trace.
        - Browser and device.
        - Application version.
        - User interaction leading to the error.
        - Related failed API requests.

    This helps identify and resolve production problems faster.

------------------------------------------------------------------------------------------------------
22. You are building a healthcare dashboard with 50+ API requests. How would you optimize its performance?
Answer:
    I would approach this in multiple layers.

    1. Data fetching:
        - Use TanStack Query for server-state management.
        - Avoid duplicate API requests.
        - Parallelize independent requests.
        - Use dependent queries only when necessary.

    2. Caching:
        - Cache frequently accessed data.
        - Define appropriate staleTime and gcTime.
        - Invalidate queries after mutations.
        - Refetch critical information when necessary.

    3. Rendering:
        - Use code splitting.
        - Lazy-load heavy components.
        - Avoid unnecessary component re-renders.
        - Use virtualization for large tables.

    4. API optimization:
        - Reduce unnecessary API calls.
        - Use pagination.
        - Consider GraphQL or backend aggregation if multiple endpoints create excessive network overhead.

    5. Monitoring:
        - Measure Core Web Vitals.
        - Track slow API requests.
        - Monitor JavaScript errors.

    Note: The objective is to reduce initial loading time, network overhead and unnecessary rendering.

23. You have a table displaying 100,000 records. How would you design it?
Answer:
    I would avoid loading all 100,000 records into the browser.

    My approach:
        1. Implement server-side pagination.
        2. Use cursor pagination if records change frequently.
        3. Implement server-side filtering and sorting.
        4. Use virtualization to render only visible rows.
        5. Debounce search input.
        6. Cache previously fetched pages.
        7. Display loading and error states.

    Why virtualization?
        Even if you fetch only 100 records, rendering hundreds or thousands of DOM elements unnecessarily can affect performance.
        Virtualization renders only the visible rows and a small buffer.
