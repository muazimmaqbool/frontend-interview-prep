Question 1:  Differences between framework-level event systems and native browser events ?
Answer:
    Native browser events are the events provided directly by the browser through the DOM API, such as addEventListener(). 
    Frameworks like React provide their own event system (Synthetic Events) that wraps native events to offer a consistent API across different browsers and optimize event handling. 
    In React, events are delegated internally, reducing the number of event listeners attached to the DOM.

    Comparison:
        | Native Browser Events                 | Framework-Level Events (React)                      |
        | ------------------------------------- | --------------------------------------------------- |
        | Uses `addEventListener()`             | Uses React's event handlers like `onClick`          |
        | Browser-specific behavior may vary    | Provides a consistent API across browsers           |
        | Attached directly to DOM elements     | Managed by React's event system                     |
        | You manually add and remove listeners | React manages listeners automatically               |
        | Uses native `Event` object            | Uses `SyntheticEvent` (wrapper around native event) |

    Example:
        
        ->Native Browser Event:
            const button = document.getElementById("btn");
                button.addEventListener("click", () => {
                    console.log("Clicked");
            });

        ->React Event:
            function App() {
            return (
                <button onClick={() => console.log("Clicked")}>
                    Click Me
                </button>
            );
            }

        ->Interview Summary:
            Native browser events use the DOM's addEventListener() API and expose the browser's Event object. 
            Frameworks like React use a Synthetic Event system that wraps native events to provide consistent cross-browser behavior and centralized event handling, 
            allowing developers to work with a simpler and more predictable event API."

Question 2: Difference Between Hooks and Higher-Order Components (HOCs)?
Answer:
    Hooks and Higher-Order Components (HOCs) are both patterns for reusing logic in React, but they work differently. 
    ->A Hook is a function that lets functional components use React features like state and lifecycle methods. 
    ->A Higher-Order Component (HOC) is a function that takes a component as input and returns a new enhanced component with additional functionality.

    ->Comparison:
        | Hooks                                            | HOCs                                   |
        | ------------------------------------------------ | -------------------------------------- |
        | Introduced in React 16.8                         | Used before Hooks for code reuse       |
        | Used inside functional components                | Wrap existing components               |
        | Share logic without changing component hierarchy | Create a new enhanced component        |
        | Simpler and easier to read                       | Can lead to "wrapper hell" if overused |
        | Preferred in modern React                        | Less common in new applications        |

    ->Hook Example (Built-in):
        useState()
        useEffect()
        useContext()
        useReducer()
        useMemo()
        useCallback()
        useRef()

    ->Built-in HOC Example:
        React.memo()
         const MyComponent = React.memo(function MyComponent(props) {
                                return <h1>{props.name}</h1>;
                            });

Question 3: How React works internally?
Answer: 
    React works by creating a Virtual DOM, which is a lightweight copy of the real DOM. 
    Whenever the state or props of a component change, React re-renders that component to create a new Virtual DOM. 
    It then compares the new Virtual DOM with the previous one using the reconciliation (diffing algorithm). 
    React identifies the minimum changes required and updates only those parts of the real DOM, making UI updates efficient and improving performance

    ->React Rendering Flow:
        Component Render
                ↓
               JSX
                ↓
        React.createElement()
                ↓
        Virtual DOM
                ↓
        State/Props Change
                ↓
        New Virtual DOM
                ↓
        Reconciliation (Diffing)
                ↓
        Minimal Real DOM Updates
                ↓
        Browser Paint

    ->Key Concepts:
        JSX → Converted to React.createElement()
        Virtual DOM → Lightweight copy of the UI
        Reconciliation → Compares old and new Virtual DOM
        Diffing Algorithm → Finds minimal changes
        React Fiber → Prioritizes and schedules updates
        Real DOM Update → Only changed elements are updated
                        
    ->Interview Summary (Best Answer):
        "Internally, React converts JSX into JavaScript objects using React.createElement() and builds a Virtual DOM.
         When state or props change, React creates a new Virtual DOM and compares it with the previous one using the reconciliation (diffing algorithm). 
         It calculates the minimum set of changes and updates only those parts of the real DOM. React's Fiber architecture further improves 
         performance by prioritizing updates and allowing rendering work to be paused and resumed, keeping the application responsive."

Question 4: Does class declaration get hoisted?
Answer:
    Yes, class declarations are hoisted, but they cannot be accessed before they are declared because they are in the Temporal Dead Zone (TDZ).

    ->Class declarations are hoisted, similar to let and const, but they are not initialized during hoisting. 
      They remain in the Temporal Dead Zone until their declaration is reached. 
      If you try to access a class before it's declared, JavaScript throws a ReferenceError.

    ->Example:
        const obj = new Person(); // ❌ ReferenceError

        class Person {
            constructor(name) {
                this.name = name;
            }
        }
        o/p: ReferenceError: Cannot access 'Person' before initialization

        const obj = new Person(); // works fine here

Question 5:  How would you optimize a slow React app?
Answer:
    When optimizing a slow React application, I first identify the bottleneck using tools like React DevTools, Profiler and Chrome DevTools instead of optimizing prematurely. 
    Then i reduce unnecessary re-renders using React.memo, useMemo, and useCallback. 
    I optimize rendering by implementing lazy loading, code splitting, and virtualization for large lists. 
    I also optimize API calls with caching, debouncing, or throttling, reduce bundle size through tree shaking, compress images, and use browser caching or a CDN.
    Finally, I monitor Core Web Vitals to ensure the optimizations improve real user experience.

Question 6: What is the difference between package.json and package-lock.json?
Answer:
    ->package.json describes the project and lists its dependencies, scripts, and metadata. It can specify version ranges like ^ or ~. 
    ->package-lock.json is generated automatically by npm and records the exact versions of every installed package and its dependencies. 
      This ensures consistent installations across different developers, machines and deployment environments.

Question 7: What is the difference between ^ and ~ in dependency versions?
Answer:
    -> ^ (caret) allows npm to install newer-> minor and patch versions while keeping the same major version. 
    -> ~ (tilde) is more restrictive and only allows patch updates within the same minor version. 
    -> We use ^ when we want to receive backward-compatible feature updates and ~ when we want only bug fixes without new features.

    | Symbol | Meaning                            | Example                          |
    | ------ | ---------------------------------- | -------------------------------- |
    | `^`    | Allows **minor and patch** updates | `^18.2.0` → `18.3.0`, `18.2.5` ✅|
    | `~`    | Allows **patch** updates only      | `~18.2.0` → `18.2.5` ✅          |

    -> ^ (Caret): Allows updates that don't change the major version.
            Example:
                {
                    "react": "^18.2.0"
                }
            npm can install:
                            18.2.1 ✅
                            18.2.5 ✅
                            18.3.0 ✅
                            18.9.1 ✅
                            19.0.0 ❌

            Rule:
                Major ❌
                Minor ✅
                Patch ✅

    ->  ~ (Tilde): Allows only patch updates.
            Example:
                {
                    "react": "~18.2.0"
                }
            npm can install:
                            18.2.1 ✅
                            18.2.9 ✅
                            18.3.0 ❌
                            19.0.0 ❌
            Rule:
                Major ❌
                Minor ❌
                Patch ✅

Question 8: How do closures affect memory usage, and when can they cause memory leaks?
Answer:
    A closure keeps references to variables from its outer scope, so those variables remain in memory as long as the closure is reachable. 
    This is useful, but if a closure is kept alive unnecessarily, it can retain large objects and cause memory leaks.

    Example:
        function createHandler() {
            const largeData = new Array(1000000).fill("data");

            return () => {
                console.log(largeData.length);
            };
        }

        const handler = createHandler();

    Here, handler keeps largeData alive because the closure references it.

    ->Common Memory Leak:
            Event listeners or timers are a common example:

            useEffect(() => {
                const handler = () => {
                // closure keeps referenced data alive
            };

            window.addEventListener("resize", handler);

            return () => {
                window.removeEventListener("resize", handler);
            };
            }, []);
            If you don't remove the listener, the browser may keep the closure and everything it references in memory.

    ->Interview One-liner:
            Closures don't inherently cause memory leaks; leaks happen when long-lived references such as event listeners, timers, or global objects 
            unnecessarily keep closures—and the data they reference—alive.

Question 9: What are Web Components, and how do they differ from React components?
Answer:
    Web Components are native browser technologies for creating reusable custom HTML elements. They work without React or any JavaScript framework.

    Example:
        class MyButton extends HTMLElement {
            connectedCallback() {
                this.innerHTML = `<button>Click Me</button>`;
            }
        }

        customElements.define("my-button", MyButton);      

    Usage:
        <my-button></my-button>    

    Web Components vs React Components:
        | Web Components                         | React Components                      |
        | -------------------------------------- | ------------------------------------- |
        | Native browser technology              | React library                         |
        | Works without a framework              | Requires React                        |
        | Uses Custom Elements, Shadow DOM, etc. | Uses JSX and React's rendering system |
        | Can be used in any framework           | Mainly used within React              |
        | DOM-based                              | React component-based                 |

    One-liner:
        Web Components are framework-independent custom HTML elements provided by the browser, 
        while React components are JavaScript components managed by React's rendering and state system.
