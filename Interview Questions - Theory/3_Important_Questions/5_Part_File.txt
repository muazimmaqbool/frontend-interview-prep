Question 1: What is difference between ' onClick={()=>setCount(count+1)} ' and ' onClick={()=>setCount((count)=>count+1)} '?
Answer:
    The difference is how React gets the previous state value.

    ->1. Using the current count:
            onClick={() => setCount(count + 1)}

            This uses the count value available in the current render.
            For a single update, it works fine.

    ->2. Using a functional update:
            onClick={() => setCount((count) => count + 1)}

            React gives you the latest previous state value as the parameter.
            This is safer when the next state depends on the previous state.

    ->Example where the difference matters:
            // May not be increment by 3
                setCount(count + 1);
                setCount(count + 1);
                setCount(count + 1);

            All three may use the same count value.

            But:
            // Correctly increments by 3
                setCount((prev) => prev + 1);
                setCount((prev) => prev + 1);
                setCount((prev) => prev + 1);

            Each update receives the latest updated value.

    ->Interview answer:
            setCount(count + 1) uses the state value from the current render, while setCount(prev => prev + 1) receives the latest previous state 
            and is preferred when the new state depends on the old state.

Question 2: How do you find memory leaks in a frontend application?
Answer:
        I use Chrome DevTools, especially the Memory and Performance tabs, to check whether memory keeps increasing after navigating, opening/closing components, or repeating an action.
        My approach:
                -> Reproduce the issue repeatedly.
                        For example, open and close a modal multiple times.
                -> Take Heap Snapshots before and after.
                        Check whether objects/components that should be removed are still retained in memory.
                -> Look for common causes:
                        -Event listeners not removed
                        -setInterval or timers not cleared
                        -WebSocket/subscriptions not closed
                        -Large objects kept in closures or global state
                        -Detached DOM nodes
                -> Fix and verify
                        Add cleanup functions and take another Heap Snapshot to confirm memory is released.

        Interview one-liner:
                I identify memory leaks by reproducing the behavior, comparing Heap Snapshots in Chrome DevTools, finding objects that remain retained unexpectedly, 
                and then checking common causes such as listeners, timers, subscriptions, and retained references.

Question 3: why index as key can cause problems?
Answer:
        Using the array index as a React key can cause problems when items are added, removed, sorted, or reordered.

        Example:
                {users.map((user, index) => (
                    <User key={index} user={user} />
                ))}

        Suppose:
                Index 0 → John
                Index 1 → Alice
                Index 2 → Bob

        Now remove John:
                Index 0 → Alice  // Previously John's key
                Index 1 → Bob    // Previously Alice's key

        React sees the same keys 0 and 1, so it may think these are the same components as before and reuse their existing DOM/component state incorrectly.

        This can cause:
                Wrong input values/state appearing on another row
                Incorrect UI updates
                Unnecessary re-renders
                Problems with animations
        
        Better:
                Use a unique and stable ID:

                {users.map((user) => (
                     <User key={user.id} user={user} />
                ))}

        Now:
           John  → key=101
           Alice → key=102
           Bob   → key=103

        Even if the order changes, Alice is always 102.

        Interview answer:
                Index as a key can cause incorrect component reuse when a list changes order or items are added/removed. 
                I prefer a unique, stable ID so React can correctly identify each item across renders.

        Note: Index is generally okay when the list is static and will never be reordered, inserted into, or deleted from.

Question 4: What is the difference between api and endpoint?
Answer:
        An API is the overall system/interface that allows applications to communicate, while an endpoint is a specific URL within that API used for a particular operation.

        Simple Example:
           Suppose you have a User API:
                API: https://api.example.com

          It contains multiple endpoints:
                GET  /users        → Get all users
                GET  /users/10     → Get user 10
                POST /users        → Create user
                PUT  /users/10     → Update user 10
                DELETE /users/10   → Delete user 10

          So you can think of it as:
                        API
                        ├── /users
                        ├── /users/:id
                        ├── /products
                        └── /orders
                                ↑
                            Endpoints
        
        Interview answer:
                An API is the complete interface through which applications communicate, 
                while an endpoint is a specific location or route in that API that performs a particular operation.

        Easy way to remember:
                API = whole restaurant menu
                Endpoint = one specific item on the menu.

Question 5: What are Suspense and Concurrent Rendering?
Answer:
        Suspense and Concurrent Rendering are modern React features that work together to make web apps load faster and feel smoother.

        ->What is React Suspense?
                Suspense is a feature that lets your components "wait" for data or code to load before showing them on the screen.
                   Fallback UI: While waiting, React shows a temporary placeholder, like a loading spinner or skeleton text.
                   Declarative Loading: Instead of writing complex if (loading) checks in every component, 
                                        you wrap the part that loads slowly inside a <Suspense> boundary.
        
        ->What is Concurrent Rendering?
                Concurrent Rendering is an engine update in React that allows React to work on multiple tasks at the same time
                   Interruptible: If React is rendering a heavy list and a user types in a box, React can pause the heavy job, handle the typing instantly, 
                                  and then go back to the list
                   Priority Scheduling: React ranks tasks by urgency. Typing and animations get high priority, while background data loading gets low priority

        ->How They Work Together:
                Concurrency gives React the ability to multitask under the hood, and Suspense gives you an easy way to display loading states while those tasks finish.

Question 6: What is the difference between Horizontal Scaling and Vertical Scaling?
            - When would you choose one over the other?
            - What are their advantages and limitations?
Answer:
        1. Horizontal Scaling (Scale Out):
                Adding more servers to handle increasing traffic.
                Example: Instead of one server handling 10,000 users, use 3 servers and distribute traffic using a load balancer.
                                     Load Balancer
                                         |
                                ┌────────┼────────┐
                                ↓        ↓        ↓
                        Server 1     Server 2  Server 3
        
                Advantages:
                        - Handles large traffic efficiently.
                        - Better availability; if one server fails, others can continue serving requests.
                        - Can scale by adding more servers.
                Limitations:
                        - More complex to manage.
                        - Requires load balancing.
                        - Shared state, sessions, and databases need careful handling.

        2. Vertical Scaling (Scale Up):
                Increasing the resources of an existing server, such as CPU, RAM, or storage.
                Example: Upgrade a server from 8 GB RAM to 32 GB RAM.
                                Before: Server (4 CPU, 8 GB RAM)
                                        ↓
                                After:  Server (8 CPU, 32 GB RAM)
                Advantages:
                        - Simple to implement.
                        - No major architecture changes.
                        - Easier to manage.
                Limitations:
                        - Hardware has a maximum capacity.
                        - Upgrades can be expensive.
                        - A single server can remain a single point of failure.

        When would I choose each?
                Horizontal Scaling	                          Vertical Scaling
                --------------------------------------------------------------------------
                Large applications with growing traffic	        Small to medium applications
                Need high availability	                        Need a quick performance boost
                Workload can run across multiple servers	Application is difficult to distribute
                Long-term scalability	                        Simpler short-term scaling

        Interview answer:
                Vertical scaling means increasing the CPU or RAM of an existing server, while horizontal scaling means adding more servers to distribute the workload.
                I would choose vertical scaling for smaller applications because it's simpler and faster to implement. 
                For large applications expecting high traffic and requiring high availability, I would prefer horizontal scaling with load balancing.
                Both can also be combined depending on the application's requirements.

Question 7: What is Load Balancing, and how does it improve application performance and availability?
            - What are common load-balancing algorithms?
            - How does a load balancer handle server failures?
Answer:
        What is Load Balancing?
                Load balancing is the process of distributing incoming requests across multiple servers so that no single server becomes overloaded.
           It improves:
                - Performance: Distributes traffic across servers, reducing overload and improving response times.
                - Availability: If one server fails, requests can be sent to healthy servers.
                - Scalability: More servers can be added as traffic increases.

           Simple Architecture:
                             Users
                                |
                                ↓
                        Load Balancer
                                |
                        ┌─────────┼─────────┐
                        ↓         ↓         ↓
                    Server 1   Server 2  Server 3
                    Healthy    Healthy   Failed ❌
                        ↑         ↑
                        └────┬────┘
                             |
                        Traffic distributed
                        to healthy servers
                
                Note: if server 3 was also working fine then traffic gets distributed among all 3 servers.

           Common Load Balancing Algorithms:
                Algorithm	                How it works
                ---------------------------------------------------
                Round Robin	              Distributes requests to servers one by one in order.
                Least Connections	      Sends requests to the server with the fewest active connections.
                Weighted Round Robin	      Sends more requests to servers with higher assigned capacity.
                IP Hash	                      Uses the client's IP address to consistently select a server.

            How does a load balancer handle server failures?
                1. Health Checks: Regularly checks whether servers are healthy.
                2. Detect Failure: If a server fails its health checks, the load balancer marks it unhealthy.
                3. Redirect Traffic: Stops sending new requests to the failed server.
                4. Recovery: Once the server becomes healthy again, it can receive requests.
           For example, if Server 2 crashes, the load balancer distributes new requests between Server 1 and Server 3.
           
           Interview Answer:
                Load balancing distributes incoming traffic across multiple servers to improve performance, scalability, and availability.
                Common algorithms include Round Robin, Least Connections, Weighted Round Robin, and IP Hash.
                A load balancer uses health checks to detect unhealthy servers and stops routing new requests to them. 
                Once a server recovers, it can be added back into rotation.

           Important: A load balancer itself can become a single point of failure, so production systems often use redundant 
                      load balancers or managed load-balancing services.

Question 9: What is Caching, and what are the different caching strategies?
            - Difference between browser caching, CDN caching, and server-side caching.
            - What are cache invalidation and TTL?
Answer:
        What is Caching?
                Caching is the process of storing frequently accessed data temporarily so future requests can be served faster without fetching or calculating the same data again.
       
        It helps improve:
                - Performance: Faster response times.
                - Scalability: Reduces load on servers and databases.
                - Cost: Reduces repeated API calls and database queries.
        
        1. Types of Caching:
                Type	                         Description	                                          Example
                --------------------------------------------------------------------------------------------------------------------
                Browser Caching	        Stores resources in the user's browser.	                Images, CSS, JavaScript files
                CDN Caching	        Stores content on servers closer to users.	        Website images, videos, static assets
                Server-Side Caching	Stores frequently requested data on the backend.	Redis caching database query results

        2. Common Caching Strategies:
                1. Cache-Aside (Lazy Loading)
                        - Application checks the cache first.
                        - If data is missing, fetches it from the database and stores it in the cache.
                        - Commonly used with Redis.
                2. Write-Through
                        - When data is updated, it is written to both the cache and database.
                        - Helps keep cached data updated.
                3. Write-Back (Write-Behind)
                        - Data is written to the cache first.
                        - The database is updated later asynchronously.
                        - Faster writes, but cached data can be lost if the cache fails before persistence.
                4. Write-Around
                        - Data is written directly to the database.
                        - Cache is updated only when data is requested again.
                        - Useful when recently written data is unlikely to be read immediately.

        3. What is Cache Invalidation?
                Cache invalidation means removing or updating cached data when it becomes outdated.
                Example:
                        User updates profile name
                                ↓
                        Database updated
                                ↓
                        Old cached profile removed
                                ↓
                        Next request fetches fresh data

                Without cache invalidation, users might see outdated information.

        4. What is TTL (Time To Live)?
                TTL defines how long cached data remains valid before it expires.
                Example:
                        // Redis example
                        await redis.set("user:101", JSON.stringify(user), {
                                EX: 300, // Cache expires after 300 seconds (5 minutes)
                        });
                After 5 minutes, Redis automatically expires the key.
                TTL vs Cache Invalidation:
                        - TTL: Automatically expires cached data after a specified duration.
                        - Cache Invalidation: Explicitly removes or updates cached data when it changes.

        Interview Answer:
                Caching stores frequently accessed data temporarily to improve performance and reduce server load.
                Browser caching stores resources locally, CDN caching stores content closer to users, and server-side caching stores frequently requested data using tools like Redis.
                Common strategies include cache-aside, write-through, write-back, and write-around.
                Cache invalidation removes or updates outdated data, while TTL defines how long cached data remains valid before expiring.
