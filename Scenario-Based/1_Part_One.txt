Question 1: How did you improve performance in your application?
Answer:
    In our healthcare EMR application, we had screens with large patient lists, appointment data, and multiple API calls. 
    Users were experiencing slow page loads and unnecessary re-renders. To improve performance:

        -> I implemented React Query caching so previously fetched data was reused instead of making repeated API calls.
        -> Added appropriate staleTime and cache settings to reduce network requests.
        -> Used React.memo, useMemo, and useCallback because expensive calculations or unnecessary re-renders were happening.
        -> Implemented lazy loading and code splitting using React.lazy and Suspense to reduce the initial bundle size.
        -> Optimized images by loading them lazily.
        -> Added pagination/infinite scrolling for large datasets instead of rendering hundreds of records at once.
        -> Moved search filtering and sorting logic into memoized computations to avoid recalculating on every render.

        As a result, screen load times improved noticeably, API requests were reduced, and the UI became much more responsive.

    ->Short Version (1 minute):
        I improved performance by reducing unnecessary API calls with React Query caching, preventing unnecessary re-renders using 
        React.memo, useMemo, and useCallback, implementing lazy loading for routes/components, and using pagination for large datasets. 
        This reduced load times and improved UI responsiveness.

Question 3: How do you structure a large React project?
Answer: 
      I structure a large React project using a feature-based architecture. 
      Each feature has its own components, pages, hooks, services/API calls, and utilities. 
      I keep shared components, common hooks, and reusable utilities in separate shared folders. 
      This improves scalability, maintainability, and makes it easier for multiple developers to work on the project

        ->Example Structure:
                src/
                ├── features/
                │   ├── auth/
                │   ├── patients/
                │   └── appointments/
                ├── components/
                ├── hooks/
                ├── services/
                ├── utils/
                ├── routes/
                └── assets/

Question 4: How do you handle authentication and protected routes?
Answer:
    I handle authentication by storing the user's token (usually JWT) after login and maintaining the authentication state using Context API, Redux, or a global state solution. 
    For protected routes, I create a wrapper component that checks whether the user is authenticated. 
    If the user is not authenticated, they are redirected to the login page; otherwise, the requested page is rendered.

    ->Simple Example:
                    function ProtectedRoute({ children }) {
                      const token = localStorage.getItem("token");

                      return token ? children : <Navigate to="/login" />;
                    }

Question 5: Your company plans to expand from 50,000 users to 5 million users. 
            The current React application is a monolith. 
            What architectural changes would you make to support scalability?
Answer:
    To scale a React application from 50K to 5M users, I would move from a monolithic structure to a more scalable architecture:
      -> Use feature-based architecture to organize code by business modules.
      -> Implement code splitting and lazy loading to reduce initial bundle size.
      -> Use CDN and caching strategies for static assets.
      -> Introduce proper state management and avoid unnecessary global state.
      -> Optimize API communication using React Query caching, pagination, and infinite scrolling.
      -> Use micro-frontends if different teams need independent development and deployment.
      -> Add performance monitoring and optimize bottlenecks using profiling tools.

    One-liner:
        I would make the frontend modular, optimize loading and rendering performance, introduce caching strategies, 
        and adopt scalable architecture patterns like feature-based structure or micro-frontends as the application grows.

Question 6: How would you handle cross-browser compatibility issues?
Answer:
    I handle cross-browser compatibility by first identifying the browser-specific issue, checking Can i Use MDN for browser support, 
    and then using progressive enhancement, fallbacks, or polyfills where necessary.

    For example:
        /* Fallback */
        display: block;

        /* Modern browser */
        display: flex;

    I also test across major browsers like Chrome, Firefox, Safari, and Edge, preferably using tools such as BrowserStack.

    One-liner:
        I use feature detection, fallbacks/polyfills, responsive CSS, and cross-browser testing rather than relying on browser-specific behavior.

Question 7: How do you prioritize technical debt vs. new features?
Answer:
  I prioritize technical debt based on its impact on users, business, and development speed. 
  If the debt causes bugs, security issues, performance problems, or blocks new features, 
  I address it first. Otherwise, I balance it with feature work by allocating some development time to technical debt in each sprint.

  Example:
    If an old component is making a new feature difficult to build, I would refactor that component first. But if the technical debt has little impact, 
    I would deliver the business-critical feature and schedule the cleanup for a later sprint.

Question 8: How do you identify and optimize a slow-loading page?
Answer:
  Short Interview Answer:
    First, I use Chrome DevTools → Lighthouse and Performance to identify what is making the page slow.

    I check:
      Network: large JS bundles, images, slow API calls.
      Performance: expensive JavaScript and unnecessary renders.
      Lighthouse: Core Web Vitals like LCP, INP, and CLS.

    Then I optimize by:
      Code splitting and lazy loading components.
      Optimizing/compressing images.
      Reducing unnecessary API calls.
      Using caching.
      Memoizing expensive calculations/components where needed.
      Virtualizing large lists.
      Removing unused JavaScript/CSS.
